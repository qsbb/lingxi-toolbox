# 音频监听（设备级捕获 + 转发 / 多设备同播）开发方案

> 状态：**全部完成** —— A1–A10 十项验收全部通过（2026-09-30）。
> 目标版本：2.3.0
> 实测环境：macOS 27.0（arm64，Mac mini M4）· Windows 11（192.168.5.55）

---

## 1. 需求

在工具箱里加一个**监听**能力：

1. **监听按钮**：一键开启/停止
2. **捕获源**：某个输出设备上**所有系统音频**（设备级 tap，不是单个 App）
3. **播放目标**：指定另一个输出设备
4. **多设备同播**：可勾选多个目标设备，同时输出

---

## 2. 可行性结论（已实测，非推断）

### 2.1 macOS —— 原生 API，**不需要装 BlackHole 等虚拟声卡**

```
捕获源设备
   │  CATapDescription(__excludingProcesses:andDeviceUID:withStream:)   ← 设备级 tap（macOS 14.2+）
   ▼
 私有 Aggregate Device（tap 作为输入 + 目标设备作为输出子设备）
   │  AudioDeviceIOProc 回调：读 tap 输入 → 写目标输出
   ▼
目标设备（可多个）
```

### 2.2 Windows —— WASAPI 环回

```
目标设备 → IAudioClient.Initialize(LOOPBACK) → IAudioCaptureClient 读包 → 转发到另一设备的 IAudioRenderClient
```

### 2.3 实测记录（全部跑通）

|---|---|---|

| macOS | 全局 tap 创建 + 读格式 | `OSStatus=0`，48kHz/2ch ✅ |
| macOS | tap 真实捕获音频 | 回调 281、非零采样 153086、峰值 0.1983 ✅ |

## 3. 关键约束（实测踩出来的）

| # | 约束 | 影响 | 对策 |
|---|---|---|---|
| C1 | **macOS 必须打包成 .app 并声明 `NSAudioCaptureUsageDescription`** | 裸可执行文件（无 bundle ID）调 `AudioDeviceStart` 会**静默失败**（返回错误码且无提示） | 已加入 Info.plist；首次使用引导授权 |
| C2 | **macOS 14.2+ 才支持进程 tap** | 老系统不可用 | 运行时探测，低于 14.2 时按钮置灰并提示 |
| C3 | **采样率不一致会变调** | 源 44.1kHz → 目标 48kHz 直接搬运会变调/爆音 | 检测不一致时插入重采样（v1 先只支持同采样率，不一致时明确提示） |
| C4 | **漂移累积** | 长期运行会逐渐产生爆音 | `kAudioSubTapDriftCompensationKey=1` + 时间戳对齐 |
| C5 | **DRM 内容抓不到** | Apple Music / Netflix 等受保护音频被系统静音 | 文档说明，非缺陷 |
| C6 | **反馈啸叫** | 源设备==目标设备 且设备带麦时会啸叫 | UI 防呆：源与目标相同时禁止启动 |
| C7 | **Windows 需宿主常驻** | 音频流是长驻资源 | 挂在 NativeHost，Flutter 只发控制指令 |
| C8 | **设备热插拔** | 拔掉目标设备后流会断 | 监听设备变化事件，自动停止并提示 |

## 4. 协议设计（扩展 NativeHost JSON Lines）

现有 `audio.*` 只有 3 个方法，新增 4 个。**协议版本仍为 1**（向后兼容，只加方法）。

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `audio.tapCapabilities` | — | `{supported, reason?, maxTargets, canCaptureDevice}` | 能力探测（供 UI 决定按钮是否可用） |
| `audio.tapStart` | `{sourceDeviceId, targetDeviceIds[], gain?}` | `{sessionId, sourceFormat, latencyMs, resampling}` | 开始监听 |
| `audio.tapStop` | `{sessionId?}` | `{stopped}` | 停止（无 sessionId 则停全部） |
| `audio.tapState` | — | `{active, sessionId?, sourceDeviceId?, targetDeviceIds[], peakL/R, droppedFrames, uptimeSec}` | 状态轮询（UI 显示电平/健康度） |

**错误码约定**（复用现有 `ErrorCode` 机制）：
- `tap_unsupported` —— 系统版本不够（C2）
- `tap_permission_denied` —— 未授权音频捕获（C1）
- `tap_source_not_found` / `tap_target_not_found` —— 设备不存在（C8）
- `tap_same_device` —— 源与目标相同（C6）
- `tap_format_mismatch` —— 采样率不一致且未启用重采样（C3）

## 5. 实现设计

### 5.1 共享层（`LX.Audio.Core`）

现有 `IAudioEndpointService` 只管设备枚举/默认设备，**新增独立的转发接口**（不污染现有契约）：

```csharp
public interface IAudioLoopbackService : IDisposable
{
    TapCapabilities GetCapabilities();
    TapSession Start(TapRequest request);
    void Stop(string? sessionId = null);
    TapStatus? GetStatus();
}
```

平台实现：
- `LX.Audio.Core/Mac/MacAudioTapService.cs` —— CoreAudio P/Invoke（tap + aggregate + IOProc）
- `LX.Audio.Core/Windows/WasapiLoopbackService.cs` —— WASAPI 环回

> ⚠️ 注意：`LX.Audio.Core` 当前是 `net8.0` 且**零依赖**（为跨平台单测），新增代码必须保持这个约束 —— 平台分支用 P/Invoke，不引第三方音频库。

### 5.2 macOS 实现要点

1. `CATapDescription(__excludingProcesses: [], andDeviceUID: sourceUID, withStream: 0)` —— 设备级捕获
2. 建私有聚合设备：`taps` 挂 tap、`subdevices` 挂目标设备、`drift=1`
3. `AudioDeviceCreateIOProcIDWithBlock` 回调里：读输入 ABL → 写输出 ABL（注意 `AudioBufferList` 的 **`mBuffers` 偏移是 8 不是 4**，之前踩过）
4. 多目标：`subdevices` 里放多个设备即可（**一条流同时输出到多设备**）
5. 增益：回调里乘系数（v1 默认 1.0）

### 5.3 Windows 实现要点

1. 每个目标设备一个 `IAudioRenderClient` 渲染流
2. 源设备一个 `IAudioCaptureClient`（`AUDCLNT_STREAMFLAGS_LOOPBACK`）
3. 共享模式格式通常是 float32；按 `GetMixFormat` 走
4. 用事件驱动（`AUDCLNT_STREAMFLAGS_EVENTCALLBACK`）而非轮询，降低延迟

### 5.4 Flutter 侧

- **服务**：`lib/services/audio_tap_controller.dart`（ChangeNotifier，复用 `MonitorController` 的定时器/降级模式）
- **UI**：音频页新增「监听」区块
  ```
  [● 监听]  ← 一键开关
  捕获源:   [Mac mini扬声器 ▾]
  播放到:   ☑ Mi monitor   ☐ USB3.0 Audio      ← 多选
  状态:     监听中 · 48kHz · ~24ms · 峰值 -18dB
  ```
- **权限引导**：`tap_permission_denied` 时弹窗说明并给出「打开系统设置 → 隐私与安全性 → 音频录制」的按钮

## 8. 风险与预案

| 风险 | 概率 | 预案 |
|---|---|---|
| C# P/Invoke 调 CoreAudio 的 `AudioBufferList` 布局出错 | 中 | 已有 Swift 原型可对照；先写最小探针验证格式再上转发 |

### ⚠️ 实现期新增的 4 个坑（都已修，重写必看）

1. **`CATapDescription.UUID` 返回 `NSUUID*` 而非 `CFUUIDRef`**
   直接传给 `CFUUIDCreateString` 会导致进程**静默挂死**（无崩溃日志）。
   正确路径：`NSUUID → UUIDString(NSString) → UTF8String(const char*)`。

2. **`CFArrayCreate`/`CFDictionaryCreate` 的回调表不能传 `IntPtr.Zero`**
   必须传 `kCFTypeArrayCallBacks` / `kCFTypeDictionaryKeyCallBacks` /
   `kCFTypeDictionaryValueCallBacks`（`NativeLibrary.GetExport` 取地址），
   否则在 retain/release 时空指针挂死。

3. **聚合设备描述字典必须保活到会话结束**
   创建后立刻 `CFRelease` 会让聚合设备被一并回收，
   后续所有属性查询返回 `'who?'`(2003332927 = kAudioHardwareBadObjectError)。

4. **`System.Text.Json` 把 `object?` 反序列化成 `JsonElement`（struct）**
   它**不实现 `IEnumerable`**，按 `IEnumerable` 判数组会拿到空列表 →
   报 `tap_target_not_found`。必须按 `JsonElement.ValueKind` 判类型。

### 已知小问题（不阻塞）

- 聚合设备刚创建时，延迟属性（`bufs`/`latn`/`safo`）在 C# 侧读不到（返回 `'who?'`），

### ⚠️ 另一个实测发现：嵌套聚合设备不可作目标

用"聚合设备"充当第二个输出目标时，IOProc **完全不回调**（丢帧 235、电平 0）。
原因：CoreAudio 不支持把聚合设备再嵌套进另一个聚合设备作为子设备。
⇒ 测试/验收必须用**真实物理输出设备**，不能用合成设备充数。

### ⚠️ 长稳测试暴露并修掉一个真 bug

**现象**：第一次 30 分钟长稳跑到 13 分钟时，`droppedFrames` 稳定以每分钟 +250 累积（累计 3451）。

## 16. ⚠️ selector 常量写错（根因级，2026-09-30）

### 现象

macOS 侧读延迟属性（buffer/latency/safety）**恒返回 0**，OSStatus = `'who?'`(2003332927)，
而同样的属性用 Swift 读**完全正常**（fsiz=512 / ltnc=60 / saft=48）。

我当时误判成"聚合设备刚创建时属性未就绪"，还专门加了 `RefreshLatency()`
（改成流启动后再读）——**方向完全错了**，问题跟时序无关。

### 根因

**四个 selector 常量我凭记忆写错了**：

| 属性 | 正确（Swift `kAudio*`） | 我写错的 |
|---|---|---|
| `kAudioDevicePropertyBufferFrameSize` | `'fsiz'` (0x6673697A) | ~~`'bufs'`~~ |
| `kAudioDevicePropertyLatency` | `'ltnc'` (0x6C746E63) | ~~`'latn'`~~ |
| `kAudioDevicePropertySafetyOffset` | `'saft'` (0x73616674) | ~~`'safo'`~~ |
| `kAudioStreamPropertyVirtualFormat` | `'sfmt'` (0x73666D74) | ~~`'vfmt'`~~ |

### 定位手法（可复用）

**用 Swift 打印系统常量的真实值**，与 C# 手写的十六进制逐位对照：

```swift
import CoreAudio
func show(_ n: String, _ v: AudioObjectPropertySelector) {
    let b = withUnsafeBytes(of: v.bigEndian) { String(bytes: $0, encoding: .ascii) ?? "?" }
    print("\(n) = 0x\(String(format: "%08X", v)) ('\(b)')")
}
show("BufferFrameSize", kAudioDevicePropertyBufferFrameSize)  // -> 0x6673697A ('fsiz')
```

一眼就看出 `'bufs' ≠ 'fsiz'`。

### 教训

- **CoreAudio 的属性选择器不要凭记忆写四字符码**。虽然 `'bufs'`/`'latn'` 读起来"很合理"，
  但它们是错的（`'latn'` 甚至对应别的属性）。一律用 Swift 常量对照生成。
- 排查时**先证伪"环境/时序"假设**：我一开始归因于"属性未就绪"，
  实际只要拿 Swift 读同一个属性就能立刻推翻（Swift 在**启动前**就读得到）。
- 与 BUG-61「同名不同皮」同类：**字面看着对 ≠ 真的对**，要有权威来源比对。

### 修复后验证

```
C# 侧读（修正后）: dev=73 fsiz=512 ltnc=60 saft=48
Swift 侧参照:      dev=73 fsiz=512 ltnc=60 saft=48   ✅ 完全一致
```

延迟字段现在返回**实测值**（不再需要 24.5ms 估算兜底，但兜底逻辑保留作为防御）。
